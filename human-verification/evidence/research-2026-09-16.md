# Documentary evidence: passkey attestation behaviour (compiled 2026-09-16)

Compiled by an automated research pass during this feasibility study. Legend: **[A]** direct quote
from vendor/spec/source; **[B]** secondary source (forum, issue tracker, library mirror, search
snippet); **[C]** inference. Several primary hosts were unreachable from the build environment
(list at the end); where a quote came through a mirror or snippet it is marked [B]. Re-verify
before relying on any single line; vendor behaviour changes.

## 1. Apple iCloud Keychain passkeys — attestation format

Consumer (non-MDM) passkeys return `fmt: "none"` even when `attestation: "direct"` is requested.

- [A] Apple staff, Apple Developer Forums thread 726208 (Mar 2023): "Passkeys generally, including
  those in iCloud Keychain, don't support attestation as it exists today … So this is expected
  behavior and is the same for most (all?) synced WebAuthn credentials currently."
  https://developer.apple.com/forums/thread/726208
- [A] Apple staff, thread 713195 (Aug 2022): "In a world where the credential can sync to devices
  with different security properties, a one-shot attestation during registration can't provide
  any meaningful promises about all of the devices where the passkey can be used."
  https://developer.apple.com/forums/thread/713195?answerId=725647022#725647022
- [A] Developer report, thread 710342 (Jul 2022): decoded object `{'fmt': 'none', 'attStmt': {}, …}`.
- [B] w3c/webauthn issue #1989 (2023-10): "Apple has moved to Passkeys starting from iOS 16 and no
  longer provides an Attestation Statement (to be precise - returns 'none')".
- [C] The `apple` anonymous attestation format is not produced for iCloud Keychain passkeys; the
  AAGUID `fbfc3007-154e-4ecc-8c0b-6e020557d7bd` ("Apple Passwords" in the community AAGUID list)
  is populated despite `none`. The hybrid/QR flow uses the same authenticator, so `none` is
  expected there too (inference).

Managed-device attestation (iOS/iPadOS 17, macOS 14): [A] WWDC23 session 10263 "Deploy passkeys at
work" and [A] Apple staff thread 731571: "a `basic` attestation in the packed format, signed by the
identity provisioned through DDM"; requires the `SecurityPasskeyAttestation` declaration
(`AttestationIdentityAssetReference`, `RelyingParties`), device enrollment and a Managed Apple
Account. The chain reaches the organisation's CA, not a public root.

Confidence: high for consumer `none`; hybrid-specific behaviour is inference.

## 2. Google Password Manager (Android / hybrid)

- [B] fido-dev thread "Details on Google's implementation of passkeys" (Google statement via
  snippet): "Passkeys on Android will not initially have any attestation." … "if attestation is
  added in the future it will be in a new format that is common across different Google products."
- [B] Microsoft Entra documentation (mirror, dated 2026-02): "Synced passkeys do not support
  attestation."
- [C] GPM returns `fmt: "none"` for `attestation: "direct"`, on-device and via hybrid.
- [A] Android developers: "The SafetyNet Attestation API was deprecated in 2022" and "fully turned
  down in January 2025" (https://developer.android.com/privacy-and-security/safetynet/deprecation-timeline).
- [B] Neither `ea9b8d66-4d01-1d21-3ce4-b6b48cb575d4` (Google Password Manager) nor
  `fbfc3007-…` (Apple Passwords) appears in MDS-derived datasets; the community AAGUID list states
  it "does not replace FIDO's Metadata Service (MDS)… Some AAGUIDs in this list may not appear in
  FIDO MDS."

Confidence: medium (Google statement via snippet; MDS absence via mirror and code search).

## 3. Windows Hello

- [B] Yubico maintainer (2022): Windows generates `tpm` attestation statements.
- [B] MDS entry copies for "Windows Hello Hardware Authenticator" (AAGUID
  `08987058-cadc-4b81-b6e1-30de50dcbe96`): attestationTypes `attca`, keyProtection `hardware`,
  matcherProtection `software`, statusReports `FIDO_CERTIFIED_L1` (2020-08-05), root "Microsoft
  TPM Root Certificate Authority 2014".
- [A] Entra docs (mirror): Windows Hello Hardware / VBS Hardware / Software authenticator AAGUIDs;
  "If attestation is enabled, only device-bound passkeys are allowed; synced passkeys are excluded."
- [B] 2018 report of `none` from Edge with AAGUID 08987058: `tpm` is not guaranteed in every path.

Confidence: medium.

## 4. WebAuthn L3 `hints` and transport evidence

- [A] Spec (w3c/webauthn main, 2026-08): `hints` "specifies hints to the user agent about what
  types of authenticators the RP prefers"; `hybrid`: "User authentication should occur via a
  hybrid transport…". `getTransports()`: "The client platform obtains the transports list based on
  the authenticator used during the registration ceremony." `authenticatorAttachment` "reports the
  authenticator attachment modality in effect at the time…".
- [C] The assertion signature covers `authenticatorData || SHA-256(clientDataJSON)` only
  (confirmed in @simplewebauthn/server 14.0.2 `verifyAuthenticationResponse.js`); transport and
  attachment are unsigned and client-reported.
- Browser support: [B] MDN compat data: `hints` Chrome 128+, Firefox and Safari not supported.
  [A] Chromium Blink IDL declares `hints`; Gecko WebIDL declares it but the handler never reads it;
  WebKit IDLs contain no `hints` member. [B] Windows 11 native UI ignores hints.

Confidence: high.

## 5. FIDO Metadata Service v3

- URL: libraries default to `https://mds.fidoalliance.org/`; `https://mds3.fidoalliance.org/` is
  the documented v3 name; both could not be fetched from this environment.
- Root CA: [B] go-webauthn issue #778: since 2026-08-21 the BLOB signing chain rotated to
  GlobalSign Root R46; libraries pinning only Root CA R3 broke. [A] @simplewebauthn/server 14.0.2
  bundles both R3 (SHA-256 CB:B5:22:D7…) and R46 (4F:A3:12:6D…).
- BLOB rules (as embedded in the library from the MDS spec): ignore the file if the chain cannot be
  verified or a chain certificate is revoked; ignore if the signature is invalid; ignore if `no` is
  not greater than the cached serial. `nextUpdate`: "date when the next update will be provided at
  latest".
- `statusReports` values: NOT_FIDO_CERTIFIED, FIDO_CERTIFIED, USER_VERIFICATION_BYPASS,
  ATTESTATION_KEY_COMPROMISE, USER_KEY_REMOTE_COMPROMISE, USER_KEY_PHYSICAL_COMPROMISE,
  UPDATE_AVAILABLE, REVOKED, SELF_ASSERTION_SUBMITTED, FIDO_CERTIFIED_L1…L3plus.
- Fields: `keyProtection` (software|hardware|tee|secure_element|remote_handle), `matcherProtection`
  (software|tee|on_chip), `userVerificationDetails` (AND-combinations of methods),
  `attestationTypes` (basic_full|basic_surrogate|ecdaa|attca|anonca|none),
  `attestationRootCertificates` (trust anchor per model).

Confidence: medium (spec HTML unreachable; definitions via library mirrors of spec text).

## 6. @simplewebauthn/server 14.0.2 behaviour (verified in the installed package)

- `MetadataService` strict mode throws "No metadata statement found for aaguid" for unregistered
  AAGUIDs, but `getStatement()` is only called from the packed, android-key, android-safetynet and
  tpm verifiers. `verifyRegistrationResponse` never consults metadata for `fmt: none` (returns
  `verified: true` when `attStmt` is empty), `apple` or `fido-u2f`.
- `validateCertificatePath` returns `true` without validating when the trust-anchor list is empty.
- Conclusion [C]: library success is not a trusted-hardware verdict; an explicit policy layer is
  required (implemented in `src/policy/attestationPolicy.ts`).

Confidence: high.

## 7. Apple Private Access Tokens / Privacy Pass

[A] Apple (2022-06-09): "Private Access Tokens are powerful tools that prove when HTTP requests are
coming from legitimate devices without disclosing someone's identity." Server: 401 with
`WWW-Authenticate: PrivateToken` including issuer hostname and public key. [A] WWDC22 10077: the
attester "performs device attestation, using certificates stored in the device's Secure Enclave,
and verifies that the account is in good standing"; "servers that receive tokens can only check
that they are valid, but they cannot discover client identities or recognize clients over time";
requires iOS 16 / macOS Ventura with an Apple ID. RFC 9576 (architecture), 9577 (HTTP auth
scheme), 9578 (token types). [C] No fresh user gesture, no identity, nothing about a separately
submitted passkey.

Confidence: high.

## 8. Chrome virtual authenticator attestation

[A] Chromium `device/fido/virtual_ctap2_device.cc` / `virtual_fido_device.cc`: response uses
`packed` with `alg -7`, `sig`, and `x5c` = one self-signed certificate (subject "C=US, O=Chromium,
OU=Authenticator Attestation, CN=Batch Certificate" or "Individual Certificate") unless
`none_attestation` is set; the CDP options expose no attestation switch. Confirmed empirically in
this study (`evidence/e2e-virtual-authenticator-2026-09-16.md`).

Confidence: high.
